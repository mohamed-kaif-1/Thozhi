## 1. Executive Summary

This independent audit conducted a comprehensive, line-by-line verification of the newly implemented [`SupabaseRepository`](file:///c:/Users/moham/OneDrive%20-%20ELCOT/Projects/Thozhi/backend/app/db/repositories/supabase.py) and [`SupabaseClient`](file:///c:/Users/moham/OneDrive%20-%20ELCOT/Projects/Thozhi/backend/app/db/supabase_client.py) against the declarative PostgreSQL schema defined across `001_initial_schema.sql`, `002_rls_policies.sql`, and `003_schema_alignment.sql`.

The audit identified **4 CRITICAL**, **3 HIGH**, and **4 MEDIUM** severity incompatibilities that would cause runtime SQL exceptions (`400 Bad Request` / `500 Internal Server Error`) or data integrity violations if connected to a live PostgreSQL instance.

### Primary Audit Findings:
1. **CRITICAL — Invalid Enum Value in `captures.processing_status`:** `SupabaseRepository.create_capture()` inserts `"COMPLETED"`. The schema type `capture_status_enum` in `001_initial_schema.sql` only permits `('RECEIVED', 'TRANSCRIBED', 'PROCESSED', 'FAILED')`. PostgreSQL will immediately reject capture ingestion with `invalid input value for enum capture_status_enum: "COMPLETED"`.
2. **CRITICAL — Missing Column in `tasks`:** `SupabaseRepository.complete_task()` sends `"actual_duration_min": act_dur` to `PATCH /tasks`. Neither Migration 001 nor Migration 003 defines `actual_duration_min` on `tasks`. PostgREST will fail with HTTP 400 (`column tasks.actual_duration_min does not exist`).
3. **CRITICAL — Unpersisted Clarification Questions:** `ProposalResponse` returns `clarifications`, but neither Migration 001 nor Migration 003 defines a `clarifications` column on `proposals` or a `proposal_clarifications` table. Clarifications generated by AI extraction are permanently lost upon proposal retrieval.
4. **CRITICAL — Migration 003 Precondition Dependency:** If Migration 003 has not been deployed to PostgreSQL, `SupabaseRepository` will immediately fail on `proposals.status = 'PENDING_REVIEW'` (invalid enum), `captures.lifecycle_status` (missing column), `tasks.origin_proposal_id` (missing column), and `memory_preferences.category` (missing column).
5. **HIGH — Non-Atomic Multi-Step Proposal Approval:** `approve_proposal()` coordinates 7 separate HTTP calls across 5 tables sequentially. A network interruption or race condition between concurrent clients causes duplicate task creation and partial failure states without rollback.
6. **HIGH — RLS Service-Role vs. Authenticated JWT Mismatch:** The current client relies on static headers. When switched to standard authenticated RLS, `002_rls_policies.sql` lacks `WITH CHECK` clauses, and `task_dependencies` allows cross-tenant task ID reference.

## 4. Foreign-Key, Relationship & Constraint Analysis

### 4.1 Missing Database-Level Uniqueness on Proposal-to-Task
- **Schema in 001:** `tasks.source_proposal_item_id UUID REFERENCES proposal_items(id) ON DELETE SET NULL`.
- **Issue:** There is no `UNIQUE (source_proposal_item_id)` constraint on `tasks`.
- **Risk:** If an approval operation is retried or executed concurrently, multiple tasks pointing to the same `source_proposal_item_id` can be inserted into the database.
- **Severity:** **HIGH**. Violates idempotent commitment invariant.
- **Remediation:** Add `CONSTRAINT uq_task_source_proposal_item UNIQUE (source_proposal_item_id)` in Migration 004.

### 4.2 Cross-Tenant Foreign-Key Tampering in `task_dependencies`
- **Schema in 001:**
  ```sql
  CREATE TABLE task_dependencies (
      id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
      user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
      predecessor_task_id UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
      successor_task_id UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
      ...
  );
  ```
- **RLS Policy in 002:**
  ```sql
  CREATE POLICY dependencies_self ON task_dependencies FOR ALL USING (user_id = current_user_id());
  ```
- **Vulnerability:** The policy only verifies `user_id = current_user_id()`. It does not check that `predecessor_task_id` and `successor_task_id` actually belong to `current_user_id()`. An authenticated user could attach dependency edges to another user's private tasks if task UUIDs are known or enumerable.
- **Severity:** **MEDIUM**. Cross-tenant graph pollution.
- **Remediation:** Add tenant consistency validation to RLS or foreign keys in Migration 004.

### 4.3 Supabase Auth Decoupling
- **Schema in 001:** `users.id UUID PRIMARY KEY`.
- **Issue:** `users.id` is not constrained by `REFERENCES auth.users(id) ON DELETE CASCADE`.
- **Risk:** Deleting an identity in Supabase Auth leaves orphaned records in `public.users`.
- **Severity:** **MEDIUM**.

## 5. Transaction Integrity & Approval Lifecycle Risks

### 5.1 Race Condition on Concurrent Proposal Approval
In [`backend/app/db/repositories/supabase.py`](file:///c:/Users/moham/OneDrive%20-%20ELCOT/Projects/Thozhi/backend/app/db/repositories/supabase.py#L391-L500), `approve_proposal()` performs the following sequence over independent HTTP requests:

```
Client Request A                     Client Request B (Concurrent / Double Click)
       |                                    |
  [1] GET /approval_idempotency (Not found) |
       |                               [1] GET /approval_idempotency (Not found)
       |                                    |
  [2] GET /proposals                        |
       |                               [2] GET /proposals
       |                                    |
  [3] POST /tasks (Creates Task UUID-1)     |
       |                               [3] POST /tasks (Creates Duplicate Task UUID-2!)
       |                                    |
  [4] PATCH /proposal_items                 |
       |                               [4] PATCH /proposal_items
       |                                    |
  [5] PATCH /proposals                      |
       |                               [5] PATCH /proposals
       |                                    |
  [6] POST /approval_idempotency (Succeeds) |
                                       [6] POST /approval_idempotency (Fails 409 Conflict)
```

**Consequence:** Even though Request B eventually receives a 409 Conflict at Step 6, **duplicate tasks (`UUID-2`) have already been created in the database** at Step 3. Because each PostgREST HTTP request is its own transaction, earlier writes are never rolled back.

### 5.2 Partial Network Failure State
If a network disconnect occurs at Step 5 (after inserting tasks and updating proposal items, but before committing `proposals.status` and `approval_idempotency`):
- `tasks` are created.
- `proposal_items` are marked approved.
- `proposals.status` remains `PENDING_REVIEW`.
- `approval_idempotency` has zero record of the approval.
- A subsequent retry will rerun the loop and create a duplicate set of tasks.

### 5.3 Architectural Solution: PostgreSQL Atomic RPC
To provide genuine ACID atomicity, proposal commitment must be encapsulated in a single database stored procedure:
`commit_proposal_atomic(p_user_id, p_proposal_id, p_idempotency_key, p_decisions)`.

## 6. Row Level Security (RLS) Policy Gaps

### 6.1 Missing `WITH CHECK` Clauses in `002_rls_policies.sql`
- **Issue:** All policies in `002_rls_policies.sql` are declared as:
  `CREATE POLICY <table>_self ON <table> FOR ALL USING (user_id = current_user_id());`
- **Vulnerability:** When `FOR ALL` is used without an explicit `WITH CHECK`, PostgreSQL applies the `USING` filter to `UPDATE` operations, but tenant reassignment attacks (`UPDATE tasks SET user_id = <victim_id> WHERE id = <attacker_task>`) can succeed unless an explicit `WITH CHECK (user_id = current_user_id())` is enforced.
- **Severity:** **HIGH**.
- **Remediation:** Recreate policies with both `USING (user_id = current_user_id())` and `WITH CHECK (user_id = current_user_id())`.

### 6.2 Service-Role vs. User JWT Execution Mode
- **Current State:** `SupabaseClient` sends `SUPABASE_KEY` (service-role key in production).
- **Security Impact:** In PostgreSQL, the `service_role` role has `BYPASSRLS`. Therefore, database-level RLS policies are **currently bypassed 100% of the time**. Tenant isolation depends entirely on FastAPI application code passing `WHERE user_id = ...`.
- **Pre-JWT Requirement:** When JWT authentication is introduced, `SupabaseClient` must accept and forward the user's bearer token on every request, so PostgREST assumes the `authenticated` role and enforces RLS at the SQL engine level.

## 7. Required Forward-Only Migration Proposal (Migration 004)

To resolve all verified schema incompatibilities without destructively modifying existing migrations `001`, `002`, or `003`, the following forward-only migration DDL is required:

```sql
-- ====================================================================
-- THOZHI MASTER MIGRATION 004: POSTGREST PERSISTENCE ALIGNMENT & ATOMICITY
-- Version: 4.0.0 (PostgreSQL 15+ / Supabase PostgREST)
-- Status: Forward-only, additive, non-destructive migration
-- ====================================================================

-- 1. EXTEND CAPTURE STATUS ENUM
DO $$ BEGIN
    ALTER TYPE capture_status_enum ADD VALUE IF NOT EXISTS 'COMPLETED';
EXCEPTION WHEN duplicate_object THEN null; END $$;

-- 2. EXTEND TASKS TABLE WITH MISSING METRICS & CONSTRAINTS
ALTER TABLE tasks ADD COLUMN IF NOT EXISTS actual_duration_min INT;
ALTER TABLE tasks ADD COLUMN IF NOT EXISTS scheduled_date DATE;

-- Prevent duplicate task creation from identical proposal items
DO $$ BEGIN
    ALTER TABLE tasks ADD CONSTRAINT uq_task_source_proposal_item UNIQUE (source_proposal_item_id);
EXCEPTION WHEN duplicate_object THEN null; END $$;

-- 3. EXTEND PROPOSALS TABLE WITH PERSISTED CLARIFICATIONS
ALTER TABLE proposals ADD COLUMN IF NOT EXISTS clarifications JSONB DEFAULT '[]'::JSONB NOT NULL;

-- 4. HARDEN RLS POLICIES WITH EXPLICIT 'WITH CHECK' CLAUSES
DROP POLICY IF EXISTS captures_self ON captures;
CREATE POLICY captures_self ON captures FOR ALL
    USING (user_id = current_user_id())
    WITH CHECK (user_id = current_user_id());

DROP POLICY IF EXISTS proposals_self ON proposals;
CREATE POLICY proposals_self ON proposals FOR ALL
    USING (user_id = current_user_id())
    WITH CHECK (user_id = current_user_id());

DROP POLICY IF EXISTS proposal_items_self ON proposal_items;
CREATE POLICY proposal_items_self ON proposal_items FOR ALL
    USING (user_id = current_user_id())
    WITH CHECK (user_id = current_user_id());

DROP POLICY IF EXISTS tasks_self ON tasks;
CREATE POLICY tasks_self ON tasks FOR ALL
    USING (user_id = current_user_id())
    WITH CHECK (user_id = current_user_id());

DROP POLICY IF EXISTS memory_self ON memory_preferences;
CREATE POLICY memory_self ON memory_preferences FOR ALL
    USING (user_id = current_user_id())
    WITH CHECK (user_id = current_user_id());

-- 5. ATOMIC PROPOSAL APPROVAL STORED PROCEDURE (RPC)
CREATE OR REPLACE FUNCTION commit_proposal_atomic(
    p_user_id UUID,
    p_proposal_id UUID,
    p_idempotency_key VARCHAR(255),
    p_item_decisions JSONB
) RETURNS JSONB AS $$
DECLARE
    v_cached_response JSONB;
    v_proposal RECORD;
    v_item JSONB;
    v_item_id UUID;
    v_is_approved BOOLEAN;
    v_task_id UUID;
    v_approved_count INT := 0;
    v_rejected_count INT := 0;
    v_created_task_ids UUID[] := '{}';
    v_now TIMESTAMPTZ := NOW();
    v_result JSONB;
BEGIN
    -- 1. Check idempotency cache
    SELECT response_payload INTO v_cached_response
    FROM approval_idempotency
    WHERE user_id = p_user_id AND idempotency_key = p_idempotency_key;

    IF v_cached_response IS NOT NULL THEN
        RETURN v_cached_response;
    END IF;

    -- 2. Validate proposal exists and belongs to user
    SELECT * INTO v_proposal
    FROM proposals
    WHERE id = p_proposal_id AND user_id = p_user_id;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Proposal % not found for user %', p_proposal_id, p_user_id USING ERRCODE = 'P0002';
    END IF;

    IF v_proposal.status IN ('APPROVED', 'COMMITTED') THEN
        RAISE EXCEPTION 'Proposal % has already been committed', p_proposal_id USING ERRCODE = '23505';
    END IF;

    -- 3. Iterate over decision items
    FOR v_item IN SELECT * FROM jsonb_array_elements(p_item_decisions)
    LOOP
        v_item_id := (v_item->>'id')::UUID;
        v_is_approved := COALESCE((v_item->>'is_approved')::BOOLEAN, TRUE);

        IF v_is_approved THEN
            v_task_id := gen_random_uuid();
            INSERT INTO tasks (
                id, user_id, source_proposal_item_id, origin_proposal_id,
                title, description, deadline, estimated_duration_min,
                duration_source, priority, status, source_language, created_at, updated_at
            ) VALUES (
                v_task_id, p_user_id, v_item_id, p_proposal_id,
                COALESCE(v_item->>'proposed_title', 'Untitled Task'),
                v_item->>'description',
                (v_item->>'deadline')::TIMESTAMPTZ,
                COALESCE((v_item->>'estimated_duration_min')::INT, 30),
                'USER_APPROVED',
                COALESCE((v_item->>'priority')::task_priority_enum, 'P2_MEDIUM'::task_priority_enum),
                'PENDING',
                'en',
                v_now,
                v_now
            );

            UPDATE proposal_items
            SET status = 'APPROVED', decision_state = 'COMMITTED'
            WHERE id = v_item_id AND proposal_id = p_proposal_id AND user_id = p_user_id;

            v_approved_count := v_approved_count + 1;
            v_created_task_ids := array_append(v_created_task_ids, v_task_id);
        ELSE
            UPDATE proposal_items
            SET status = 'REJECTED', decision_state = 'REJECTED',
                rejection_reason = COALESCE(v_item->>'rejection_reason', 'User rejected item')
            WHERE id = v_item_id AND proposal_id = p_proposal_id AND user_id = p_user_id;

            v_rejected_count := v_rejected_count + 1;
        END IF;
    END LOOP;

    -- 4. Update proposal status
    UPDATE proposals SET status = 'COMMITTED' WHERE id = p_proposal_id AND user_id = p_user_id;

    -- 5. Update capture lifecycle status if linked
    IF v_proposal.capture_id IS NOT NULL THEN
        UPDATE captures SET lifecycle_status = 'COMMITTED' WHERE id = v_proposal.capture_id AND user_id = p_user_id;
    END IF;

    -- 6. Build response payload
    v_result := jsonb_build_object(
        'proposal_id', p_proposal_id,
        'approved_tasks_count', v_approved_count,
        'rejected_items_count', v_rejected_count,
        'created_task_ids', to_jsonb(v_created_task_ids),
        'message', 'Human decision recorded atomically. Tasks explicitly committed to schedule.'
    );

    -- 7. Record idempotency
    INSERT INTO approval_idempotency (id, user_id, idempotency_key, proposal_id, response_payload, created_at)
    VALUES (gen_random_uuid(), p_user_id, p_idempotency_key, p_proposal_id, v_result, v_now);

    -- 8. Write audit log
    INSERT INTO audit_logs (id, user_id, event_type, metadata, created_at)
    VALUES (gen_random_uuid(), p_user_id, 'PROPOSAL_COMMITTED', jsonb_build_object('proposal_id', p_proposal_id, 'tasks_count', v_approved_count), v_now);

    RETURN v_result;
END;
```
